# ADR 006: internal authentication and server-side price

**Status:** accepted. Closes the documented gap "payments has no authentication, takes user, seats and price from the request body, and is not behind the gateway". Amends ADR 003 (the idempotency key is still a unique column, but the stored value is scoped by user, and a repeat is only "the same request" if it carries the same event and seats).

## Problem
`POST /payments` was open to anybody who could reach port 3103. Four consequences:
1. Anybody could charge any user for any seats: `userId` came from the body and nothing tied it to an admitted user.
2. The client chose the price. `amountCents: 1` for a seat that costs 50 was accepted, charged and confirmed.
3. The idempotency key was global. A second caller who knew or guessed another user's key got that payment's `paymentId` and status back (a read of someone else's payment), and the saga would never be run for their own body. The first fix (a 409 for a different user) closed the read but left squatting: an admitted attacker who posted a predictable key (`pay-<user>-1`) first made the victim's real request fail with a permanent 409, a denial of service on one user's payments.
4. The seat list accepted duplicate ids (`[5,5,5]`), and the amount is `seats x price`, so one seat could be priced several times before inventory refused the confirm.

## Decision
**Payments is an internal service; the gateway is its only client.**
- **Gateway route** `POST /events/:eventId/pay`: the same admission token as holds and confirm (403), then the per-user limiter (429, 503 when the limiter store is down: fail closed), then the body checks. The body `userId` must be the token's user (403); a body `eventId`, if present, must be the path's event (400), and a missing one is filled in from the path; `Idempotency-Key` is required (400) and passed through. The gateway calls payments `POST /payments` with the correlation headers and the internal credential.
- **Internal credential:** header `x-internal-token` must equal `PAYMENTS_INTERNAL_TOKEN` (default `dev-internal-token`, refused with `NODE_ENV=production`, same rule as `ADMISSION_SECRET`). It is checked in a Fastify `onRequest` hook, which runs before the body is read, parsed or validated and before any database access, so an unauthenticated caller gets 401 even for a malformed body and learns nothing about the validation rules. Default deny: everything except `/healthz`, `/readyz` and `/metrics` needs the token, including `/admin/psp`. The comparison hashes both sides with SHA-256 and uses `timingSafeEqual`, so the lengths are equal and the secret's length and prefix do not leak through timing.
- **Input validation:** seat ids must be 1 to 8 distinct positive int4 values; a duplicate id is a 400 before anything is charged, because the price is `seats x price` and a repeated id would be billed repeatedly. The gateway needs no such check: it forwards the body, and payments is the single place that validates and prices it.
- **Server-side price:** `amountCents = seatIds.length x SEAT_PRICE_CENTS` (default 5000, positive integer). `amountCents` in the body is optional; if present it must equal the computed value, otherwise 400. Clients that already sent the right price keep working, a tampered one is rejected before anything is charged. The stored and charged amount is always the computed one.
- **Idempotency key scoping:** payments derives the key it stores, looks up and sends to the PSP (also as `refund:<key>`) from the user and the client key: `<length of userId>:<userId>:<client key>`. The length prefix makes the pair unambiguous (user `a:b` + key `c` and user `a` + key `b:c` are different keys), so no (user, key) pair can collide with another and a key chosen by one user can never block another's. No migration: the column stays a plain global unique text. Another user sending the same client key creates an independent payment and never sees the first one. For the same user, when the key exists the stored `event_id` and seat set (order ignored) must equal the request's; otherwise 409 `idempotency key reused with a different request`, with no data about the stored payment. The same key with the same request returns the stored result exactly as before. The amount is not compared: it follows from the seats and the price, and comparing it would turn a price change between two retries into an error.

## What this does not fix
- **Seat-hold ownership is verified only at confirm.** *(Superseded by [ADR 007](007-verify-holds-before-charging.md): payments now asks inventory before charging; the text below describes the state when this ADR was written.)* Payments does not ask inventory who holds the seats before charging. An authenticated user can still pay for seats another user holds: the card is charged, inventory refuses the confirm (owner check) and the saga refunds (ADR 005). The end-to-end suite keeps this scenario ("cheaters") on purpose. Checking before the charge would add a call to the hot path and still race with expiry, so the compensation would stay.
- **The internal token is a shared secret, not an identity.** Anybody who holds it can call payments as the gateway, with any user and seats. There is one secret for all callers, no rotation mechanism, and nothing binds it to a network peer.
- The token proves who was admitted for the event, not that this person owns the card; the PSP is a fake.

## Rejected alternatives
- **Mutual TLS between the gateway and payments.** The right production answer (identity per workload, rotation, no secret on the wire), but it needs a CA, certificate issuance and rotation, and a mesh or per-service TLS config that the lab does not have; the lab would be demonstrating certificate plumbing rather than the payment design. Named as the production upgrade; the shared token has the same enforcement point (an `onRequest` hook) so it can be replaced without touching the controller.
- **A signed JWT (or the admission token) forwarded to payments.** It would let payments see the user and drop the body `userId`, and it carries an expiry. But it adds key distribution and a verifier library to a second service, the admission token is bound to an event and a waiting-room decision, not to a payment, and a replayable bearer of a user's identity inside the network is a bigger leak than a service secret. The gateway already did the user check; payments needs to know "the caller is the gateway", not who the user is.
- **Trusting the network** (payments on a private network, no credential). One misrouted port mapping, a compromised neighbour or a developer's `curl` bypasses the whole edge policy: the admission token, the limiter and the body check. In the lab every service listens on the host, so any local process can reach payments: the lab itself is the counter-example.
- **Keeping the amount from the client but checking it against a price list afterwards.** The same rule with one more place where the two can disagree; computing it removes the field's authority entirely. The optional field is kept only for backward compatibility.
- **Scoping the idempotency key by user in the unique index** (`UNIQUE (user_id, idempotency_key)`). It needs a migration, and the PSP key would still have to be scoped separately. Scoping the value inside payments gives the same semantics (another user's replay creates their own payment) without a schema change. This replaces the earlier decision to answer 409 for a different user, which let a squatter block a victim.
- **Answering 409 when only the user differs** (the first version of this ADR). It hid the stored payment but let an attacker who posted a predictable key first block the victim's real request permanently.
- **Returning 200 with the stored result when only the user differs** (treat the key as a capability). Anyone who learns a key reads the payment; keys are chosen by clients and appear in their logs.

## Addendum (2026-11-07): the static header became a request signature
The shared `x-internal-token` header was replaced by `x-internal-auth`, an HMAC-SHA256 over `timestamp, method, path, SHA-256(body)` with `PAYMENTS_INTERNAL_TOKEN` as the key (`packages/platform/src/internal-auth.ts`; verification in two hooks, `onRequest` for the cheap freshness check and `preParsing` for the signature over the raw body, capped at 64 KiB).
- **What it fixes:** the secret no longer travels on the wire or shows up in a proxy log; a captured header cannot be used for another body, path or method, and stops working after 30 s. Rotation is possible: `PAYMENTS_INTERNAL_TOKEN_PREVIOUS` is accepted in addition to the current key.
- **What it does not fix:** it is still one shared key. Whoever holds it can sign any request as the gateway; payments cannot tell callers apart, and there is no binding to a network peer. The identical request can be replayed inside the 30 s window; for `POST /payments` the idempotency key makes that harmless (the stored result is returned), for `POST /admin/psp` it is not, and that endpoint exists only with `PSP_ADMIN=1`. Clock skew above 30 s between gateway and payments makes every payment 401.
- **Cost:** the gateway hashes and signs one body per payment, and payments reads the body into memory before parsing it (a few hundred bytes). A smoke run of `scripts/bench.sh payments 1` after the change showed 0 failed requests; throughput was later re-measured on a busy machine (PSP 0 ms: 912 RPS against 959 before; PSP 100 ms: 521 against 536, 3% to 5% lower, not isolated from the load); the HMAC itself costs about 2.4 microseconds to sign and 3.2 to verify, and an A/B on inventory (which uses the same hooks) measured 0.4% to 6.7% lower throughput for the signed tree (see [benchmarks](../../../docs/benchmarks.md#request-signing-measured-as-an-ab-on-the-same-machine)).
- **Rejected:** mutual TLS (needs certificate management the lab does not otherwise have); a signature without the body (a captured header could be paired with a different body); JWT (adds a library and claims we do not use).
