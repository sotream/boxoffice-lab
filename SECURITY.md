# Security

This is a learning and design lab, not a production system. Do not deploy it as is.

Known gaps that are deliberate and documented (see "Limits of this lab" in the README and `docs/e2e.md`):

- Payments authenticates its caller with a request signature (`x-internal-auth`: HMAC-SHA256 over timestamp, method, path and body, key `PAYMENTS_INTERNAL_TOKEN`, 30 s skew), not with mutual TLS. The key is never sent and a captured header cannot be reused for another request or after 30 s, but it is still one shared key: anybody who holds it can sign calls as the gateway, with any user and seats, and payments cannot tell its callers apart. A rotation is supported with `PAYMENTS_INTERNAL_TOKEN_PREVIOUS` (payments accepts both keys while the gateway is switched).
- Inventory authenticates its callers the same way (inventory [ADR 002](services/inventory/adr/002-signed-internal-requests.md)): every route except the probes needs `x-internal-auth`, signed with `INVENTORY_INTERNAL_TOKEN`, a key of its own, so a key leaked from payments does not open inventory and the other way round. The gateway and payments sign; it is still one shared key per callee (inventory cannot tell the gateway from payments, and anybody who holds the key can confirm seats for any user), an identical request can be replayed inside the 30 s window (`confirm` is idempotent, a replayed hold is refused while the hold is live), and the extra HMAC costs inventory about 0% to 7% of its throughput on an M1 (3.6% on average over the four hold scenarios, measured as an A/B; see [benchmarks](docs/benchmarks.md#request-signing-measured-as-an-ab-on-the-same-machine)). Rotation: `INVENTORY_INTERNAL_TOKEN_PREVIOUS`.
- Seat-hold ownership is checked before the charge (payments ADR 007), so an authenticated user paying for seats another user holds ends with a FAILED payment and an untouched card. The check is a snapshot and is skipped when inventory does not answer, so the old path (charge, confirm refused, refund; ADR 005) remains for that window and the end-to-end suite keeps exercising it.
- The payment provider is an in-process fake.
- Default secrets (`ADMISSION_SECRET=dev-secret`, `PAYMENTS_INTERNAL_TOKEN=dev-internal-token`, `INVENTORY_INTERNAL_TOKEN=dev-inventory-internal-token`, database `lab:lab`) are for local use only. In `NODE_ENV=production` the services refuse the default admission secret and the default internal tokens.
- The ops endpoints (`/metrics`, `/readyz`) expose internal counters and dependency errors and must stay off public networks.

Closed (see [payments ADR 006](services/payments/adr/006-internal-authentication-and-server-side-price.md)): payments used to accept any caller and to take user, seats and price from the request body. Now the only client is the gateway route `POST /events/:id/pay` (admission token, per-user limiter, body user must be the token's user); payments requires a signed request (`x-internal-auth`) before it parses the body, computes the amount itself (`seats x SEAT_PRICE_CENTS`) and scopes the idempotency key by user (another user's replay of a key is an independent payment, so nobody can squat a key) and answers 409 when the same user replays a key with another event or seats; duplicate seat ids are refused with 400. The ports are still open on the host in this lab: the token, not the network, is the control.

Closed (see [inventory ADR 002](services/inventory/adr/002-signed-internal-requests.md)): inventory used to accept any caller on its port: anybody who could reach it could confirm seats for any user, hold seats outside the gateway's admission token and limiters, and read availability. Now every route except the probes needs a signed request (a key separate from payments'), and an unsigned, tampered, stale or wrongly keyed request is 401 before any handler or database access. The ports are still open on the host in this lab: the key, not the network, is the control.
