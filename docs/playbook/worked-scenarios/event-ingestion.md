# Worked scenario: event ingestion (write-heavy telemetry)

[paper design] No code in this repo implements this system: every figure below is derived from stated assumptions with the formulas in [`packages/capacity`](../../../packages/capacity/src/index.ts), or borrowed from a measured component and cited. Nothing here was run.

Load shape: sustained, write-dominated, append-only, rarely read individually, read mostly as aggregates. Volume, not contention, is the problem. Matching shape in the playbook: [workload-to-architecture.md](../workload-to-architecture.md) (write-heavy / streaming). Related: [data-store-selection.md](../data-store-selection.md), [reliability-patterns.md](../reliability-patterns.md), [numbers-to-know.md](../../numbers-to-know.md).

Labels: [measured] lab figure with its source file, [derived] arithmetic shown, [folk] common ballpark not measured here, [paper design] a design with no code here.

## Requirements

Functional
- Devices send events (metric samples, state changes) over HTTPS.
- Query: dashboards over time ranges and aggregates per device or per group; occasional raw lookup of one device for debugging.
- Data older than the online window is kept cheaply or dropped.

Non-functional (assumptions)
- 1M devices, each producing 1 event every 10 s: 100 000 events/s average. Peak factor 3 (reconnect storms after an outage are the cause; a reconnect storm can be worse, see backpressure).
- Event size 200 B. Devices batch 6 events per request, one request per device per minute.
- Ingest acknowledged only after the event is durable in the log. Data visible in dashboards within 60 s.
- Raw events kept 7 days online, 1-minute aggregates kept 90 days online, raw archived 1 year.
- Loss budget: zero for billing-class events, sampling allowed for debug-class events.

## Design

Components: stateless ingest API (9 instances at peak), partitioned log (Kafka-compatible, as in the notifications service), consumers that write batches to a columnar time-series store, a rollup job producing 1-minute aggregates, object storage for archived raw data in a columnar file format, a query API over the store.

Data model: events carry `(device_id, ts, type, payload, event_id)`; `event_id` is generated by the device (uuid or device-sequence) so the pipeline can deduplicate. Store partitioned by day, ordered by `(device_id, ts)`.

Key decisions

1. Batch at every hop; commits and requests, not bytes, are the unit of cost.
   - Device to ingest: 6 events per request cuts requests 6x (100 000 to 16 667 per second [derived]).
   - Ingest to log: producer `linger` of tens of milliseconds, compression on.
   - Consumer to store: insert batches of 5 000-50 000 rows. The reason is the one measured in the lab: payments are limited by 3 commits per payment ([payments RESULTS.md](../../../services/payments/RESULTS.md), 904 RPS), so per-row commits are never acceptable at this volume.
2. Partitioned log between ingest and store. Rejected: ingest writing straight to the store. A store slowdown or restart would back up into the devices; the log is the shock absorber, and replay after a bug is possible ([notifications adr/001](../../../services/notifications/adr/001-kafka-for-notifications.md): replay and several independent consumers later, which is exactly the use here). Partition key `device_id` keeps per-device order. Choose the partition count for the peak up front (24): raising it later reorders keys.
3. Store: columnar time-series store. Rejected: Postgres for raw events (the storage and commit arithmetic in the last table row). Postgres stays for metadata (device registry, alert rules).
4. Retention tiers, decided by arithmetic on cost per access pattern.
   - Hot, raw, 7 days, 1.5 TB compressed: debugging and recent dashboards.
   - Warm, 1-minute aggregates, 90 days, 810 GB: dashboards beyond a week.
   - Cold, raw as columnar files in object storage, 1 year, 78.8 TB: audit and reprocessing, queried rarely and slowly.
   - Beyond a year: delete, or keep only hourly aggregates. State the rule in the data policy, not in code comments.
5. Idempotent writes. At-least-once delivery from the log means duplicates; dedupe on `event_id` within the batch and by a unique key or a merge-on-key table engine in the store. Same rule as notifications ([adr/002](../../../services/notifications/adr/001-kafka-for-notifications.md): at-least-once plus a dedup key; [measured] 0 duplicate rows in [notifications RESULTS.md](../../../services/notifications/RESULTS.md)).
6. Poison events (malformed payload) go to a dead-letter topic and the offset moves on, so one bad event cannot stall a partition ([notifications ADR 003](../../../services/notifications/adr/001-kafka-for-notifications.md); measured: 10 poison messages gave exactly 10 dead letters).
7. Backpressure, in order of preference.
   - The log absorbs bursts; the signal is consumer lag, alert when lag in seconds (lag / consume rate) exceeds the 60 s freshness target.
   - The ingest API has a bounded in-flight limit (Little's law: 16 667 req/s x 0.02 s = 333 in flight at average, [derived]); beyond it respond 503 with `Retry-After` and jitter, rather than queue in memory.
   - Devices retry with exponential backoff plus jitter; a reconnect storm of 1M devices in 60 s is 16 667 req/s, the average rate, which is why 3x peak headroom is sufficient only if the jitter window is at least 60 s.
   - Drop policy by event class: sample or drop debug events first, never billing events. Rejected: unbounded in-memory buffering in the ingest API, which converts overload into out-of-memory crashes (the lab's gateway failure drill is the same lesson: fail fast, not hang, [failure-drills.md](../../failure-drills.md) drill 1).
8. If the log is unavailable, ingest returns 503 fast; devices keep a local ring buffer for a bounded time. The outbox trick from [payments](../../../services/payments/adr/001-saga-over-2pc.md) does not apply (there is no database transaction to join), so the device buffer is the equivalent.

## What breaks at x10

x10 means 10M devices, 1M events/s average, 3M peak, 600 MB/s peak.

1. First bottleneck: partition count, hence consumer parallelism.
   - 24 partitions x 25 000 events/s per consumer = 600 000 events/s ceiling [derived], which is x2 of the x1 peak (300 000) and only x1.2 with 0.6 headroom (24 x 25 000 x 0.6 = 360 000).
   - At x10: consumers = `instances --peak 3000000 --per-instance 25000` = ceil(200) = 200; partitions by bytes = 600 / (10 x 0.6) = 100 [derived].
   - Change: a new topic with at least 200 partitions and a cutover (replay old topic into new, or dual-consume); do it before x2, because adding partitions to a live keyed topic reorders keys.
2. Second bottleneck: the ingest tier and network.
   - Requests: 500 000 per second at peak, `instances --peak 500000 --per-instance 10134` = ceil(82.2) = 83 instances [derived]; bandwidth 600 MB/s = 4.8 Gbit/s, which exceeds a single 1 Gbit or even 2.5 Gbit load balancer path [derived]; spread across load balancers and zones.
   - Change: edge aggregation (regional ingest that batches several devices before the log) or a longer device batch window (12 events per 2 minutes halves requests; 2 minutes of extra latency against a 60 s freshness target needs a product decision).
3. Third bottleneck: cost of the cold tier. 788 TB for one year of raw events (10 x 78.8) [derived]. Change: shorten raw retention to 90 days and keep aggregates, or sample non-billing events at the device; either is a data policy change, decide it before volume arrives.

## What would be measured first

1. Consumer write rate to the chosen store, the single placeholder that sets partitions and cost: a Node bench modelled on [services/notifications/load/bench.js](../../../services/notifications/load/bench.js) (it produces events into a 3-partition topic, runs consumers, and verifies counts, duplicates and dead letters). Variables: batch size (500, 5 000, 50 000), partitions consumed (1, 3, 6), with 200 B events. Output: events/s per consumer, to replace the 25 000.
2. Ingest handler capacity: k6 script `load/ingest.js` posting 1.2 KB batches, copy [services/gateway/load/overhead.js](../../../services/gateway/load/overhead.js) (a short constant-VU script with a BASE variable) and run it direct vs through the load balancer; report RPS and p99 per instance to replace the 10 134 proxy.
3. Compression ratio on a sample of real events, by writing 10M synthetic events with the real field cardinalities (the 8x is a guess until then).
4. Failure drills: stop the store, then the broker, under load, copying [drills/kafka-down.mjs](../../../drills/kafka-down.mjs) and [drills/consumer-kill.mjs](../../../drills/consumer-kill.mjs): measure the catch-up time against the 3 600 s arithmetic above.

## Where this is proven in the repo / what is still paper

Proven (other components): a keyed log with consumers whose throughput scales with partitions, 447 to 1 393 deliveries/s for 1 to 3 partitions, dedup and dead-lettering with exact counts ([notifications RESULTS.md](../../../services/notifications/RESULTS.md)); catch-up after a broker outage, 300 events in 1.2 s ([failure-drills.md](../../failure-drills.md) drill 2); consumer kill without loss or duplicates (drill 3); 3 commits per payment as the evidence for batching ([payments RESULTS.md](../../../services/payments/RESULTS.md)).

Still paper: the ingest API, the columnar store, the rollups, retention tiers, the per-consumer rate, the compression ratio, backpressure behaviour under a real reconnect storm, all x10 figures. The notifications consumer figures are 20 ms-latency sends on a laptop and say nothing about store insert rates.
